# System Functionality Audit — Findings

*Generated 2026-07-06. Method: full read of backend (32 files), web-dashboard (45), mobile-app (11) and 37 SQL migrations, with every finding cross-checked against the **live** Supabase project (`tpfvnerrjhqwipyonngf`) using **read-only** queries. No test data was written and no data was modified, per agreed scope.*

Expense/imprest tables live in the `finance` schema (not `public`). Live sizes at audit time: `finance.expenses`=1,911, `finance.imprest_requests`=1,027, `finance.po_payments`=115, `public.employees`=73, `public.projects`=42.

Legend: **C**=Critical, **H**=High, **M**=Medium, **L**=Low. Items marked *(live-confirmed)* have production data proving the impact.

## CRITICAL / HIGH

### C1 — WhatsApp reply-approval handler uses obsolete routing *(live-confirmed: 12 stranded rows)*
`backend/src/routes/whatsappWebhook.js` — `handleStageApproverReply` (lines 240–304)
The inbound "YES/NO" WhatsApp handler was never updated for the 3-tier + founder-gate routing:
- **Finance "YES" → `current_stage='s3_approved'` (line 243).** `s3_approved` is a dead stage: no queue reads it, and `/:id/pay` requires `founder_approved`. It also sets `status='approved'`, **bypassing the founder gate**. **12 production imprests are currently stranded at `s3_approved`** — unpayable and invisible to Finance.
- **S1 "YES" → `s2_pending` always (line 241),** ignoring `approval_route`. A non-HO ≤₹9,999 request should go to `s3_pending`; a >₹9,999 to `director_pending`. Instead it lands in Ritu's S2 queue, where `s2-approve` rejects it (route isn't `s2_finance_founder`) → stranded.
- **Legacy route names (lines 279, 283):** branches test `avisha_director_finance` / `avisha_ritu_finance`, which do not exist in live data (real routes are the `*_founder` variants). So S2 notifications and `founder_review_status='pending'` never fire.
- **Wrong-item risk:** with no ref_id in the reply, it approves the *latest* pending item at that stage (line 257). Same pattern in `handleFounderDirectorReply` (line 182).

**Fix:** Route WhatsApp approvals through the same transitions as the HTTP handlers in `imprest.js`. Finance approve → `founder_review_pending` (not `s3_approved`); S1 approve → `resolveImprestRouting` result; require a ref_id match (don't fall back to "latest"); update the route-name branches to the `*_founder` values. Then reconcile the 12 stranded rows (see Data Cleanup).

### H2 — Ref-ID race, no unique constraint *(live-confirmed: 14 duplicate rows)*
`backend/src/utils/refIdGenerator.js` (lines 9–47)
Ref-IDs are generated by "SELECT max(seq) → +1 → insert" with no lock/sequence, and `ref_id` has **no unique index** on either table. Two same-day submissions (or a double-tap) collide. **7 `HSE-…` ref_ids are already duplicated (14 rows).**
**Fix:** add a `UNIQUE` index on `ref_id`; generate via a Postgres sequence per day, or insert with retry-on-conflict. Dedupe existing rows before adding the constraint.

### H3 — A duplicate *warning* upgrades a *blocked* expense into the review queue
`backend/src/routes/expenses.js` (~line 188)
`else if (autoAction === 'manual_review' || duplicateResult.warnings.length > 0)` is evaluated such that a confidence-`blocked` receipt that *also* trips a soft duplicate warning becomes `manual_review` instead of `blocked`. Low-confidence / likely-fraud receipts leak into Finance's queue as approvable.
**Fix:** make `blocked` win — check `autoAction === 'blocked'` (and BLOCK-level duplicates) before the warning branch.

### H4 — `finance-send-for-review` strands HO/Bangalore imprests (latent)
`backend/src/routes/imprest.js` (lines 1654–1655)
Always resets to `current_stage='s1_pending'` regardless of route. For an HO/Bangalore item (`s2_finance_founder`), S1's `s1-approve` has no branch for that route (lines 1019/1023), so it never writes a new stage — the item sticks at `s1_pending` while the API falsely reports "forwarding to Director." No rows hit this yet (no `s2_finance_founder` item has been founder-rejected), but the logic is broken.
**Fix:** re-enter `s2_finance_founder` items at `s2_pending`; give `s1-approve` a guard/branch for that route.

### H5 — Web dashboard has no per-route role guards
`web-dashboard/src/App.jsx` (`ProtectedLayout`, lines 56–68) + `pages/S2QueuePage.jsx:258`
`ProtectedLayout` only checks `if (!user)`. Any authenticated role can open any route. Worse, `S2QueuePage` does `ROLE_CFG[role] || ROLE_CFG.approver_s2`, so read-only `head` (and `founder`, `procurement_finance`) inherit the S2 write config and see active **Forward/Reject** buttons on the board (the `/api/imprest/board` GET allows `head`). Clicks 403 at the backend, but a read-only role should never be shown write actions.
**Fix:** add a role→allowed-routes guard in `App.jsx`; make the `S2QueuePage` config fall back to a read-only view for unknown roles.

## MEDIUM

### M1 — Note columns split across `s1_note`/`s1_notes` and `s2_note`/`s2_notes` *(live-confirmed: 33 rows)*
HTTP handlers write the **singular** (`s2_note`, `imprest.js:1304`); `s2/history` (line 1266) and the WhatsApp handler read the **plural** (`s2_notes`). Both columns exist, so no crash — but **33 rows have `s2_note` set and `s2_notes` NULL**, so S2 history shows blank notes for them, and every new HTTP S2 approval will too.
**Fix:** pick one column, backfill the other, and read with a `COALESCE`/`||` fallback everywhere.

### M2 — Dashboard aggregations truncate at the 1,000-row cap *(live-confirmed: both tables exceed 1,000)*
`backend/src/routes/dashboard.js` by-site (51–53), by-category (78–82), by-status (107–109) and the imprest equivalents (373–420, drill-downs 532–579); `expenses.js` finance/adjustments (321–326). These do a plain `.select()` and reduce in JS with no pagination, unlike sibling endpoints that use `fetchAllRows`. With 1,911 expenses and 1,027 imprests, every one of these charts silently under-counts.
**Fix:** use `fetchAllRows` (already in `utils/fetchAll.js`) for all aggregation reads.

### M3 — Head dashboard KPIs are wrong
`backend/src/routes/head.js`
- `pendingDirectorApprovals` (115–119) filters `current_stage='s2_pending' AND founder_review_status='pending'`. Real director items are at `director_pending` (**5 live**) → KPI reads 0.
- `paidThisWeek` (129, 172) sums PO `total_amount` instead of `paid_amount` → overstates cash on partial payments.

### M4 — Weekly/monthly reports mis-count the pipeline
`backend/src/routes/reports.js` (57–60, 118–119)
Pipeline query selects only `s1_pending, s2_pending, s3_pending` (omits `director_pending`, `founder_review_pending`), and the S2/Director counters filter on the non-existent `avisha_ritu_finance`/`avisha_director_finance` routes → **"S2 · Ritu" and "Director" are always 0** in the founder's summaries.

### M5 — Head "All Imprest" list omits early-pipeline requests
`web-dashboard/src/pages/HeadImprestListPage.jsx:49` → `imprest.js:643`
Uses `finance/queue`, whose server-side stage filter excludes `s1_pending`/`s2_pending`/`director_pending`. Page titled "All Imprest" shows an incomplete list with no indication of filtering.

### M6 — Head Kanban drops `founder_approved` and keeps a dead column *(live-confirmed: 38 rows)*
`web-dashboard/src/pages/HeadKanbanPage.jsx` (61–68)
No `founder_approved` column → **38 approved-awaiting-payment imprests disappear** from the board; the `s3_approved` "Approved–Unpaid" column is dead (stage no longer produced by the normal flow).

### M7 — Founder-review / WhatsApp handlers have no stage guard
`backend/src/routes/imprest.js:1758` (`/:id/founder-review`) and `whatsappWebhook.js:200`
Unlike every other transition, these don't check `current_stage` before moving the item. A replayed/stale n8n call or a mis-matched WhatsApp reply can knock an already-paid or already-rejected request back to `s3_pending` / `director_rejected`.
**Fix:** assert the expected current stage before transitioning; make the update idempotent.

### M8 — Amount reductions overwrite `amount_requested` in place
`imprest.js` s2-approve (1307), s2-override (1136), director-approve (1389)
Reducing the approved amount mutates `amount_requested`, losing the original ask and breaking the `isPartial` check in finance-approve (`finalAmount < imp.amount_requested`, line 827) — it can never flag "partially approved" after a prior reduction.
**Fix:** store reductions in a dedicated column (e.g. `s2_adjusted_amount` exists; `director_approved_amount` exists) and keep `amount_requested` immutable.

### M9 — Imprest `/submit` doesn't validate `site`
`backend/src/routes/imprest.js` (252–254)
Expenses and register call `isValidSite(site)`; imprest submit accepts any string. Combined with M10, a stale/mismatched default site is silently accepted and can mis-route.
**Fix:** validate `site` via `isValidSite()` and reject unknown values.

### M10 — Mobile imprest site default comes from a different list than the picker
`mobile-app/app/(app)/imprest.jsx:142` (+ `src/constants/index.js`)
`site` initializes to `IMPREST_SITES[0]` (`'MAX Hospital, Saket Delhi'`) while the picker renders `useSites()` (`/api/projects`). On Android the displayed option can differ from submitted `site` if the user doesn't touch the picker. Also the bundled fallback `SITES` lacks `'Bangalore Office'`, so on cold-start/offline a Bangalore user can only pick `'Bangalore Branch Office'`, which routes to S1 instead of S2. *(Note: the live `/api/projects` DOES contain `'Bangalore Office'` and `'Head Office'`, so the online path is correct — this only bites on the fallback path. There are also two Bangalore sites in `projects`, only one of which forces S2.)*

### M11 — Duplicate-txn BLOCK is case/whitespace-sensitive
`backend/src/services/duplicateService.js:44`
`.contains('screenshot_metadata', { transactionId })` is an exact JSONB match, while `verificationService.checkTransactionId` treats IDs case-insensitively. The same UPI/UTR read as `abc123` vs `ABC123` won't match → the same payment can be claimed twice.
**Fix:** normalize (upper + trim) transactionId on store and on the dup query.

### M12 — PO procurement Stage-1 is dead *(live-confirmed: 0 of 115)*
`backend/src/routes/poPayments.js` — ingest sets `status='pending_payment'` (112) while `/procurement-queue` and `procurement-approve/reject` gate on `pending_procurement` (166, 253, 311). No PO is ever at `pending_procurement`, so those endpoints are unreachable and the procurement gate is skipped. **Confirm whether this is intentional.**

### M13 — Procurement approve/reject swallow errors; S1 sidebar link dead-ends
`web-dashboard/src/pages/ProcurementQueuePage.jsx` (184–198, 476–487) — no `catch`, so failures show no toast; the modal just resets. Separately, the `approver_s1` sidebar links to `/procurement-queue`, which 403s for S1 and renders permanently empty with no message (`Sidebar.jsx:20`).

### M14 — WhatsApp phone normalization mishandles leading "91"
`backend/src/services/whatsappService.js:28`
`normalised.startsWith('91') ? normalised : '91'+normalised` treats any leading 91 as a country code. A 10-digit Indian mobile starting with 91 stays 10 digits → invalid recipient, approver never notified.
**Fix:** normalize on length (prefix `91` only when length === 10).

## LOW / hygiene

- **L1** Founder-gate straight approve requires no note (only when amount changes) — `imprest.js:1544` — inconsistent with "notes required at every stage."
- **L2** Expense "Search" filter is client-side over the current 50-row page only (never sent to backend); "Select all" selects rows not visible under an active search. `ExpenseQueue.jsx` (281–314), `expenseService.js`.
- **L3** Verification edge cases: multi-image `ocrConf = …||50` coerces a genuine 0 to 50 (`expenses.js:167`); a `FAILED` payment can still reach `manual_review`; ref-id/day resets on **UTC** not IST; date parser assumes DD/MM.
- **L4** Imprest `/submit` sets `current_stage`/`approval_route` in a **second, unchecked** update (`imprest.js:363–377`) — brief null-stage window; if that update fails the item is invisible to all queues.
- **L5** Login "employees can't use this portal" block is cosmetic — `AuthContext.login()` sets `user` first, so `/login`'s `<Navigate>` redirects the employee anyway. `Login.jsx:21`, `App.jsx:78`.
- **L6** Employee-filter dropdown is empty for `head` (calls `/api/employees`, guarded to finance; 403 swallowed). `FilterBar.jsx:12`.
- **L7** Pagination "Next" off-by-one: `disabled={items.length < 50}` enables Next on an exactly-full final page → empty next page. Head list pages.
- **L8** Several audit-log `oldValue` fields are hardcoded and don't reflect the real prior state (`imprest.js:880`, `:1811`).
- **L9** `database/*.sql` files are stale vs applied migrations: `034_founder_approval_routes.sql` omits `s2_finance_founder` (the current primary S2 route); duplicate migration numbers exist (two `012_`, `017_`, `037_`). Rebuilding schema from the folder would produce a constraint that rejects today's data.
- **L10** RLS is disabled on `finance.imprest_weekly_overrides` and a `finance.approver_backdata_swap_*` table (Supabase advisor). Low impact since the backend uses the service-role key, but flag for defense-in-depth.
- **L11** `current_stage` CHECK still permits orphan stages `s1_approved`/`s2_approved`/`s3_approved`/`director_approved` that the normal flow never uses — this is what let C1 write `s3_approved` with no DB error. Consider tightening once code is fixed.
- **L12** `expenses.status='auto_verified'` is filtered on read in many places but is **never written** (submit writes `'verified'`); 0 live rows. Harmless dead branch / naming drift.
- **L13** `useWebSocket` defaults `VITE_WS_URL` to `ws://localhost:4000` independent of `VITE_API_BASE_URL`; in a deploy that only sets the API URL, the live-update socket reconnect-loops against localhost. Verify deploy config.

## What was verified as working correctly
- Auth (`auth.js`) + `roleGuard` factory: JWT verified, profile loaded, inactive accounts blocked, backend write endpoints correctly role-scoped (the gaps above are UI-exposure and workflow, not broken backend authz).
- `resolveImprestRouting` threshold logic (`> 9,999`) is correct — no off-by-one; it is the single source of truth for the HTTP submit path.
- Verification scoring thresholds (`≥94` / `≥70`) match docs; `overallConfidence` can't become `NaN`.
- All frontend service methods and mobile endpoints map to real backend routes — **no 404/missing-endpoint bugs**; Multer field names match (`screenshots`, `screenshot`); auth token attached on every request; logout clears it.
- The uncommitted `mobile-app/app/(app)/imprest.jsx` "remove 'Others'" change is complete and internally consistent — no dangling refs, no empty-site submit path.
- All DB tables/columns referenced by the audited routes exist in the live `finance` schema — no schema-drift crashes.
- Client + server both enforce required notes on S1/S2/Director/Finance imprest actions and the expense modal (the one gap is the founder straight-approve, L1).
